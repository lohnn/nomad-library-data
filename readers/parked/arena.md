# Axiell Arena

Feasibility: NO (no reader written). Swedish Arena deployments sit behind a JavaScript challenge wall that answers non-executing clients within 1-3 requests per session, whether paced (1.1 s) or not, with or without full browser headers (`Sec-Fetch-*`, laguage, referer). A plain Node `fetch` gets real HTML for a while, then a 200 with no HTML body.

What answered: status 200, 1 400-1 600 bytes, obfuscated JS (`p+=.../p-=...` integer soup, no form, no title) instead of the requested page, `Set-Cookie` none of use to non-executing clients. Measured on three real hosts: bibliotek.nykoping.se (challenge on the search result URL right after a clean POST), bibliotek.osthammar.se (same, first pagination carry), bibliotek.hultsfred.se (challenge already on the first GET of /search). A real browser (headless Chrome) executes the challenge and reads everything fine, so the wall is client-classification, not per-access throttling. Not tested from a fresh IP (GitHub runner egress); if someone can measure over a day there and the challenges stay away, the lead below might be enough to build the reader.

The catalog behind the wall (measured on bibliotek.nykoping.se; the docs if the wall ever moves):
- Search: no GET deep link at all. GET `/search` renders a Wicket form; POST to its `action` (session-scoped `wicket:interface` URL + `p_auth`) with hidden fields (`id__simpleSearch_..._hf_0`, `hiddenQuerySource`) and `containerSearchQuery:textSearchQuery=<q>`; 302 to `search?p_p_id=searchResult_WAR_arenaportlet&p_p_lifecycle=1&...&p_r_p_arena_urn%3Aarena_search_query=<q>`; then GET that URL. Pagination links on the result page are per-session Wicket interface URLs (`...pageLink...ILinkListener`), so a reader would need session stickiness; page size 20 here (config, not a request param).
- Count: "Din sökning gav N träffar". Rows: `.arena-record` with `.arena-record-id` (UUID), `.arena-record-title`, `Medietyp:` label in `.arena-record-media`.
- Filters: "Utökad sökning" (`/extended-search`, Wicket form too) has a fixed media-class `<select>` with stable internal keys (`book`, `dvd`, `artefact`, `otherMaterial`, `video`...). All of Nyköping's film/collection is one class: blu-rays are catalogued as Medietyp "DVD" (searched "blu-ray": 4 hits, all labeled DVD); games don't exist in the collection (0 signals across all 2 000 dvd+övrigt records).
- Record detail (one page per record): `GET /results?p_p_id=crDetailWicket_WAR_arenaportlet&p_p_lifecycle=1&...&p_r_p_arena_urn%3Aarena_search_item_id=<uuid>&p_r_p_arena_urn%3Aarena_agency_name=<AGENCY>` gives `Inne:` (copies in), `Antal reservationer:` (holds), plus `Anmärkning`/`Omfång` notes (useful to split dvd/bluray/tv). Availability is not on the result list.
- Covers: stateless `GET /o/arena-portlet/portletResources?resource=resourceCover&portalSiteId=<siteId>&recordId=<uuid>&agencyName=<AGENCY>&width=0&height=0`; a 154-byte placeholder gif when a title has no art (Nyköping: 38 of 1 687 titles have art).
- Titles use Swedish punctuation `title : subtitle`.

Site-side wiring that does work and became PR: `catalog.js` SYSTEMS entry (`/_WAR_arenaportlet/`) + a `find` of the catalog's own search page (Wicket means the title can't ride in a link), and `library.js` PAGE_SIGNS entry + accepting "bibliotek"/"biblioteca"/"kirjasto" in the title-derived library name. Pasted Arena links are then recognized and named on the site with the normal "Check at <library>" hold buttons, which open the catalog in the visitor's own browser (the challenge only concerns programs).
